# 图像渲染与实时合成技术

## 1. YUV 色彩空间

YUV 是视频领域使用最广泛的色彩编码方式，它的设计源于一个巧妙的历史观察：人眼对亮度的敏感度远高于对色彩的敏感度。基于这个特性，YUV 将图像分解为亮度分量（Y，即 Luma）和两个色度分量（U 和 V，即 Chroma），然后对色度分量进行有损压缩——这就是所谓的色度子采样。

YUV420P 是流媒体中最常用的子采样格式，它每四个亮度像素共享一组色度信息，数据量仅为同等分辨率 RGB 的一半。在平面存储模式下，Y、U、V 三个分量分别存储在独立的连续内存区域中，而不是交错排列。这意味着处理 Y 分量时不需要跳过 U 和 V 字节，对缓存友好。Y 平面的分辨率等于图像分辨率，U 和 V 平面的宽高各为 Y 平面的一半。例如一张 1920×1080 的 YUV420P 图像，Y 平面占 1920×1080 字节，U 平面和 V 平面各占 960×540 字节。

YUV 和 RGB 之间的转换不是简单的线性映射，需要乘以色彩矩阵。BT.601 是标清时代的标淮，BT.709 是高清时代的标准，两者在转换系数上有微小差异。此外还有全范围（Full Range，Y 值域 0-255）和有限范围（TV Range / Limited Range，Y 值域 16-235）的区别。混淆色彩矩阵会导致画面偏色，混淆范围会导致画面发白或发暗。流媒体推流通常使用 BT.709 + Limited Range 组合。

## 2. OpenGL 视频渲染管线

OpenGL 渲染视频帧的核心思路是将 Y、U、V 三个平面分别作为独立的单通道纹理上传到 GPU，然后在片段着色器中完成 YUV 到 RGB 的转换。

具体流程如下。首先为 Y、U、V 三个平面各创建一个 GL_TEXTURE_2D 纹理，内部格式为 R8（单通道 8 位无符号整数），分别上传三块数据。纹理的宽高不同——Y 纹理宽高等于图像尺寸，U 和 V 纹理的宽高为图像尺寸的一半。上传数据时需要注意行跨度，如果帧数据的实际行跨度与纹理宽度不一致，就需要使用 GL_UNPACK_ROW_LENGTH 指定真实的字节跨度，或者在 CPU 端做逐行拷贝。

片段着色器接收三个采样器（sampler2D），根据当前像素的纹理坐标分别从 Y、U、V 纹理中采样。三个采样值构成一个 YUV 三元组，乘以色彩矩阵转换为 RGB。矩阵系数由 BT.601 或 BT.709 标准决定，通常以 uniform 变量传入着色器，方便运行时切换。如果使用有限范围，还需要先做范围扩展——将 Y 从 16-235 映射到 0-255，UV 从 16-240 映射到 0-255——再乘以色彩矩阵。着色器最终输出 vec4(r, g, b, 1.0) 写入帧缓冲。

Qt 框架提供了 QOpenGLWidget 作为 OpenGL 渲染的宿主控件。它继承自 QWidget，内部管理一个独立的 OpenGL 上下文，通过 paintGL 虚函数驱动绘制。在绘制函数中，首先绑定着色器程序，然后绑定三个纹理单元，上传 YUV 数据（glTexSubImage2D），设置顶点坐标和纹理坐标，最后调用 glDrawArrays 完成一次帧的渲染。顶点坐标通常设为填充整个控件的矩形，纹理坐标从 0 到 1。如果要保持视频源的宽高比居中显示（contain 模式），需要在顶点坐标计算时做黑边填充——根据控件尺寸和视频尺寸的比率，缩小顶点矩形的尺寸并在视口内居中。

## 3. SwsContext 像素格式转换

FFmpeg 提供的 libswscale 库是视频像素格式转换的专用工具，核心数据结构是 SwsContext（转换上下文）。它内部封装了源格式到目标格式的转换算法、缩放算法以及所需的临时缓冲区。

使用 SwsContext 的典型步骤是：先调用 sws_getContext 根据源宽高、源像素格式、目标宽高、目标像素格式和缩放算法创建上下文。缩放算法有多个选项——SWS_BILINEAR 是双线性插值，速度快、质量尚可，适合实时处理；SWS_BICUBIC 质量更高但速度慢一些；SWS_FAST_BILINEAR 更快但有轻微锯齿。创建上下文后，调用 sws_scale 函数即可完成一帧的转换。sws_scale 接收源数据和目标数据的指针数组以及各自的步长数组，在内部执行格式转换和缩放。

常见的转换场景包括：将 DXGI 桌面捕获得到的 BGRA 格式转为 YUV420P 用于推流编码，或者在编码前将视频帧缩放到不同的分辨率。SwsContext 可以多次复用，只要帧尺寸和像素格式不变，不需要每次重建，这样可以避免反复的内存分配和参数初始化开销。

## 4. DXGI 桌面复制

DXGI（DirectX Graphics Infrastructure）的 Desktop Duplication API 是 Windows 平台上获取屏幕内容最高效的方式。它工作在 GPU 层面，直接复制显卡帧缓冲中的桌面合成画面，避免了从 GPU 到 CPU 再回到 GPU 的低效路径。

工作流程如下。首先通过 D3D11CreateDevice 创建 D3D11 设备和设备上下文，然后通过 IDXGIOutput1 的 DuplicateOutput 方法获取一个 IDXGIOutputDuplication 接口指针——这是桌面复制能力的核心凭证。采集循环中调用 AcquireNextFrame 获取当前桌面的最新帧，该函数接受一个超时参数，在桌面画面静止时会一直等到有新帧或超时返回，从而避免空转浪费 CPU。获取到的帧以 IDXGIResource（实际上是 ID3D11Texture2D）的形式持有，数据仍在 GPU 显存中。

要将显存中的纹理数据读到 CPU 内存，需要一个暂存纹理作为中转。创建与桌面纹理同尺寸的 Staging 纹理，设置 Usage 为 D3D11_USAGE_STAGING 且 CPUAccessFlags 为 D3D11_CPU_ACCESS_READ。通过设备上下文的 CopyResource 将采集到的纹理拷贝到暂存纹理，然后 Map 方法将暂存纹理的像素数据映射到 CPU 可访问的地址空间，memcpy 到本地缓冲区后 Unmap 解除映射。这一步是整个路径中开销最大的环节——从 GPU 显存读取数据到系统内存的带宽是固定瓶颈。

DXGI 支持多种像素格式。最常见的是 BGRA8（B8G8R8A8_UNORM），每个像素 4 字节，B、G、R、A 各占一个通道。在 HDR 显示器上，可能遇到浮点格式如 R16G16B16A16_FLOAT，这些格式需要进行色调映射才能转为 SDR 的 BGRA8，否则画面会过曝或信息丢失。Desktop Duplication API 还有一个重要特性：当显示配置发生变化（如分辨率改变、显示器插拔或休眠唤醒）时，Duplication 接口会失效并返回 DXGI_ERROR_ACCESS_LOST 错误，此时必须释放旧接口，重新创建 D3D11 设备和 Duplication，才能继续捕获。

## 5. 实时视频帧合成

视频帧合成的本质是将多个视频源的画面按照指定的位置和大小，合并为一帧新的视频帧。在不使用 GPU 渲染的情况下，最直接的方式是在 CPU 端进行软件合成——这正是 YUV 域合成的实现方式。

合成的核心操作是 YUV420P 帧的缩放和放置。每个视频源输出的是独立的 YUV420P 帧，合成时需要将其缩放后放入目标帧的对应区域。缩放通常使用最近邻插值（Nearest Neighbor），因为它速度最快且对于实时推流来说精度损失不可见。具体做法是：对于目标帧中属于该源区域的每个像素，根据缩放比率反向映射到源帧的对应位置，取最近的像素值写入。操作分为 Y 平面和 UV 平面独立进行——Y 平面的缩放比率为目标区域尺寸除以源帧尺寸，UV 平面的缩放比率相同但涉及的尺寸都是 Y 平面的一半。

缩放并放置完成后，目标帧中未被子窗口覆盖的区域（即空白区域）统一填充黑色——YUV 空间中的黑色对应 Y=0、U=128、V=128（8 位量化下），不是全零。合成后的完整 YUV420P 帧即可送入视频编码器进行编码推流。

这一整个流程涉及的底层技术环环相扣：DXGI 从 GPU 获取桌面像素，SwsContext 将其转为 YUV420P，OpenGL 将 YUV 帧渲染到屏幕供用户预览，帧合成引擎将多个源的 YUV 帧合并为一帧，最后送入硬件编码器压缩为 H.264 码流。整个管线中的大部分操作都在 GPU 和 CPU 之间精心平衡，以最小化延迟和资源消耗。
