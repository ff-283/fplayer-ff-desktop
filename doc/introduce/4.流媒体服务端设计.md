# 流媒体服务端设计

## 第一部分：功能模块设计

### 1. 模块总览

流媒体服务端（fplayer-ff-service）是整个 FPlayer 系统的核心枢纽，负责流媒体分发、会话管理和地址编排。系统采用"内核 + 网关 + 管理界面"的组合架构，包含以下核心模块：

```
┌──────────────────────────────────────────────────────┐
│                 流媒体服务端功能模块                    │
├────────────┬────────────┬────────────┬──────────────┤
│ 媒体分发   │ 会话管理   │ 地址编排   │ 管理界面     │
│ 内核模块   │ 模块       │ 模块       │ 模块         │
│ (ZLMedia   │ (Gateway   │ (Host      │ (Electron UI │
│  Kit)      │  API)      │  Select)   │  + kernel-   │
│            │            │            │  console)    │
├────────────┼────────────┼────────────┼──────────────┤
│ 服务启动   │ 健康检查   │ 日志管理   │ 调试诊断     │
│ 编排模块   │ 模块       │ 模块       │ 模块         │
└────────────┴────────────┴────────────┴──────────────┘
```

### 2. 媒体分发内核模块（ZLMediaKit）

**功能描述**：作为系统的数据面核心，负责所有媒体协议的接入和分发。

**核心能力**：
- **RTMP 推流接入**：接收来自桌面客户端的 RTMP 推流
- **RTMP 拉流分发**：对外提供 RTMP 协议拉流
- **HTTP-FLV 分发**：将 RTMP 流实时转封装为 FLV 格式，通过 HTTP chunked 传输输出
- **HLS 分发**：将 RTMP 流切片为 TS 分片，生成 M3U8 播放列表
- **RTSP 支持**（Linux）：支持 RTSP 协议的推流和拉流
- **高性能转发**：C++ 实现，支持 epoll/iocp 事件驱动，单机数千并发

**配置管理**：
- 基于模板 `config.ini`，运行时动态替换端口配置
- 输出运行时配置文件 `run/zlm.runtime.ini`
- 支持 RTMP/HTTP/HTTPS/RTSP 端口的独立配置

### 3. 会话管理模块（Gateway API）

**功能描述**：Gateway 是控制面的核心，提供 RESTful HTTP API 管理流会话的完整生命周期。

**核心能力**：

#### 3.1 流会话 CRUD

| 操作 | HTTP 方法 | 端点 | 说明 |
|------|----------|------|------|
| 创建 | POST | `/api/v1/streams/start` | 幂等创建，返回推拉流地址 |
| 查询 | GET | `/api/v1/streams/{id}/status` | 查询指定流的状态和地址 |
| 列表 | GET | `/api/v1/streams` | 列出所有流会话 |
| 停止 | POST | `/api/v1/streams/{id}/stop` | 标记流为 stopped 状态 |
| 解析 | GET | `/api/v1/streams/resolve` | 按 app+stream 解析播放地址 |

#### 3.2 会话数据结构

```go
type streamRecord struct {
    ID            string            // 16字符 hex 唯一 ID
    App           string            // 应用名，默认 "live"
    Stream        string            // 流名，默认 "stream001"
    PublishHost   string            // 发布主机地址
    ServiceMode   string            // direct / broadcast / httpflv
    PublisherMeta map[string]any    // 发布者元信息
    SourceMeta    map[string]any    // 来源元信息
    CreatedAt     time.Time         // 创建时间
    Status        streamStatus      // running / stopped
    PlayURLs      map[string]string // 多协议播放地址
}
```

#### 3.3 幂等性保证

创建流时，Gateway 先检查是否已存在同 `app`+`stream` 且状态为 `running` 的会话。若存在则直接返回已有会话信息（200 OK），不创建新记录，不返回冲突错误。这使得客户端可以安全地重复发起创建请求。

#### 3.4 三种服务模式

- **direct**：直连模式，仅生成 RTMP 地址
- **broadcast**：广播分发模式，生成 RTMP + HTTP-FLV + HLS 全协议地址
- **httpflv**：HTTP-FLV 转换模式，额外侧重 HTTP-FLV 输出

### 4. 地址编排模块（Host Select）

**功能描述**：在多网卡、跨网段、公网代理等复杂网络环境下，智能选择可达的发布主机地址。

**核心能力**：

#### 4.1 地址来源优先级

1. **公网代理覆盖**（最高优先级）：通过 `SERVICE_PUBLIC_HOST` 环境变量或 API 请求中的 `publicHost` 参数指定
2. **启动阶段选定地址**：服务启动时通过网卡可达性探测选定的默认地址
3. **请求级动态选择**（Linux）：根据请求特征动态选择最优地址
4. **回退策略**：使用 HTTP Host 头 → `X-Forwarded-Host` 头 → `localIPv4()`

#### 4.2 Linux 多网卡选择算法

```
1. 提取客户端 IP（X-Forwarded-For 或 RemoteAddr）
2. 路由优选：UDP 拨号到客户端 → 获取内核选定的本地接口地址
3. 同子网匹配：筛选与客户端 /24 同子网的本地 IP，TCP 可达性探测
4. 轮询回退：对全部候选 IP 进行轮询 TCP 探测
```

#### 4.3 公网代理支持

当服务端部署在内网但需要通过公网访问时（FRP 隧道/Nginx 反向代理），Gateway 提供公网代理模式：
- 环境变量 `SERVICE_PUBLIC_HOST` 启动时生效
- UI 中"公网代理"复选框可在运行时动态切换
- 启用后，所有对外返回的播放 URL 使用公网地址

### 5. 管理界面模块

服务端提供两种管理界面形态，适应不同的部署场景。

#### 5.1 Electron UI（桌面管理界面）

**功能描述**：基于 Electron 的桌面管理窗口，提供可视化的流管理操作。

**页面结构**：
- **创建流面板**：选择服务模式、输入 app/stream、配置公网代理
- **当前流信息面板**：展示推流/拉流地址、一键复制按钮
- **日志监视面板**：实时查看 Gateway 日志、ZLM 日志、UI 错误日志

**UI 特性**：
- 适配 Cohere 设计系统的深色/浅色主题（localStorage 持久化）
- 按需启动：窗口打开不自动启动服务，点击按钮才拉起 ZLM + Gateway
- 流地址一键复制（带 Toast 反馈）
- 启动状态实时显示（轮询 1.2 秒间隔）

#### 5.2 Kernel Console（命令行管理界面）

**功能描述**：独立的 Go 控制台程序，用于在命令行环境部署和管理服务。

**核心特性**：
- 前台驻留运行，接收 Ctrl+C 优雅停止
- 自动探测服务根目录（从可执行文件路径向上搜索）
- 动态端口分配和配置注入
- Gateway 健康检查重试（最多 8 个候选端口）
- 自动创建默认流（`live/stream001`）
- 格式化打印可复制的链接表格

### 6. 服务启动编排模块

**功能描述**：管理 ZLMediaKit 和 Gateway 子进程的生命周期。系统提供了三条启动链路。

#### 6.1 开发态启动（PowerShell/Bash 脚本）

`scripts/start-all.ps1`（Windows）/ `scripts/start-all.sh`（Linux）：
1. 校验依赖（MediaServer 可执行文件、Gateway 可执行文件、Node.js）
2. 自动探测空闲端口（RTMP/HTTP/HTTPS + Gateway）
3. 基于模板生成运行时 ZLM 配置
4. 启动 ZLM → 等待就绪 → 启动 Gateway → 健康检查重试
5. 写入 PID 文件和 `run/runtime.json`
6. 可选启动 Electron UI

#### 6.2 Electron UI 内置编排

`ui/main.js` 在主进程内完成：
1. 窗口打开时不自动启动服务（`coreStartupStatus = idle`）
2. 用户点击"创建并开始"触发启动
3. 端口探测 → 启动 ZLM → TCP 端口健康检查（轮询 RTMP 端口，10s 超时）
4. ZLM 就绪后启动 Gateway → HTTP 健康检查（自动换端口重试）
5. 写入 `run/runtime.json`
6. Gateway URL 回写到 UI 输入框

#### 6.3 Kernel Console 编排

`kernel-console/main.go` 独立完成全部编排逻辑，不依赖外部脚本或 Node.js 运行时，适合纯命令行环境。

### 7. 日志管理模块

**功能描述**：集中管理各子进程的日志输出。

**日志分类**：
- `logs/zlm.log` + `logs/zlm.err.log` — ZLMediaKit 标准输出和错误输出
- `logs/gateway.log` + `logs/gateway.err.log` — Gateway 标准输出和错误输出
- `logs/ui.err.log` — Electron UI 错误输出

**日志查询 API**：Gateway 提供 `/api/v1/debug/logs` 端点，可远程查看最近的日志内容（可配置条数限制，默认 200 行，最大 2000 行）。

### 8. 健康检查与监控模块

**功能描述**：提供服务存活状态的检测和运行时信息的查询。

- `/healthz`：健康检查端点，返回 `{"status":"ok"}`
- `/api/v1/debug/network`：网络调试信息端点，返回发布地址、端口、代理状态、操作系统等诊断信息
- `run/runtime.json`：运行时端口和端点快照，供外部消费者（桌面端、移动端）读取

## 第二部分：技术选型

### 1. 技术栈概览

| 组件 | 技术 | 版本 | 选型理由 |
|------|------|------|---------|
| 媒体内核 | ZLMediaKit | 预编译二进制 | 高性能 C++ 流媒体服务器，支持全协议，生产级稳定性 |
| 网关服务 | Go | 1.22 | 标准库 HTTP 服务器，零外部依赖，并发安全，部署简单 |
| 控制台启动器 | Go | 1.22 | 进程管理、信号处理、跨平台兼容 |
| 管理界面 | Electron | 31 | Chromium 运行时，跨平台桌面窗口，Node.js 进程管理 |
| UI 打包 | electron-builder | 24 | Windows Portable + Linux AppImage 一键打包 |
| 辅助服务（可选） | Docker | — | docker-compose 可启动备用的 SRS 容器 |

### 2. 选型分析

#### 2.1 为什么选择 ZLMediaKit

- **全协议支持**：原生支持 RTMP/RTSP/HLS/HTTP-FLV/WebRTC 等主流流媒体协议
- **高性能**：基于 C++11 epoll/iocp 事件驱动架构，单机数千并发
- **轻量无依赖**：无需外部数据库或中间件，开箱即用
- **开源活跃**：国产开源项目，社区活跃，文档完善
- **可嵌入**：作为独立可执行文件运行，通过配置文件管理，与上层解耦

#### 2.2 为什么选择 Go 语言

- **标准库 HTTP 服务器**：`net/http` 生产级 HTTP 服务器，无需第三方框架
- **并发模型**：goroutine + channel + sync 原语，天然适合网络服务
- **零依赖部署**：编译为单一可执行文件，不依赖运行时或外部库
- **交叉编译**：`GOOS=windows/linux` 一键交叉编译
- **简洁性**：gateway 仅 860 行代码，kernel-console 仅 650 行代码，逻辑清晰可维护

#### 2.3 为什么选择 Electron

- **跨平台桌面窗口**：一套代码同时生成 Windows 和 Linux 的桌面管理界面
- **进程管理能力**：Node.js 的 `child_process.spawn` 可直接管理 ZLM 和 Gateway 子进程
- **丰富的 UI 生态**：可使用 HTML/CSS/JS 构建现代化界面
- **成熟打包工具**：electron-builder 支持 Portable EXE 和 AppImage 格式

#### 2.4 为什么无数据库

当前版本刻意不引入外部数据库：
- **简化部署**：无需安装配置 MySQL/Redis，降低运维门槛
- **场景匹配**：服务分发模式的会话生命周期短，内存存储满足需求
- **扩展预留**：Gateway 的数据访问层可未来扩展 Redis/MySQL 持久化

### 2. 控制面与数据面分离

这是系统的核心架构原则：

- **控制面（Gateway）**：仅处理 HTTP 请求，管理会话元数据，生成播放地址。完全不介入媒体数据传输。
- **数据面（ZLMediaKit）**：独立处理所有流媒体协议，完成 RTMP 推流接入、HTTP-FLV/HLS 分发。不需要知道 Gateway 的存在。
- **通信方式**：两者通过环境变量传递端口信息（`ZLM_RTMP_PORT`、`ZLM_HTTP_PORT`）。Gateway 不调用 ZLM 的任何 API，ZLM 不回调 Gateway。

这种设计的好处：
- 控制面和数据面可以独立故障恢复
- 可以替换数据面内核而不影响上层 API（例如从 ZLMediaKit 切换到 SRS）
- 可以独立扩容（Gateway 可横向扩展，ZLM 可多实例）
- 清晰的测试边界

### 3. 内存存储设计

Gateway 使用 `map[string]*streamRecord` + `sync.RWMutex` 实现会话的内存存储：

```go
var (
    mu      sync.RWMutex
    streams = map[string]*streamRecord{}
)
```

**并发安全**：
- 读操作（status/list/resolve）使用 `mu.RLock()` / `mu.RUnlock()`
- 写操作（start/stop）使用 `mu.Lock()` / `mu.Unlock()`
- 公网代理状态使用独立的 `publicHostMu sync.RWMutex`

**读写分离**：startHandler 中先加读锁检查幂等性，读锁释放后再在必要时加写锁创建新记录，避免长时间持有写锁。

**无过期机制**：当前版本不自动清理 stopped 或过期的会话，所有记录保留到 Gateway 重启。

### 4. 进程编排设计

#### 4.1 启动流程

```
1. 检测服务根目录（detectLayout / getManagedPaths）
2. 确保 run/ 和 logs/ 目录存在
3. 动态分配空闲端口
   - getFreePort(1935) → RTMP
   - getFreePort(8080) → HTTP
   - getFreePort(8443) → HTTPS
   - getFreePort(8554) → RTSP (Linux only)
4. 从模板 config.ini 生成 run/zlm.runtime.ini
5. 启动 ZLMediaKit（spawn / exec.Cmd.Start）
6. TCP 端口健康检查（等待 ZLM 端口可用）
7. 启动 Gateway（自动换端口重试，最多 8 次）
8. HTTP 健康检查（GET /healthz，200ms 轮询，5s 超时）
9. 写入 run/runtime.json
```

#### 4.2 优雅停止流程

```
1. 接收 Ctrl+C / SIGTERM
2. 向 gateway 子进程发送 os.Interrupt
3. 等待 1.5 秒
4. 若未退出，强制 kill
5. 向 ZLM 子进程发送 os.Interrupt
6. 等待 1.5 秒
7. 若未退出，强制 kill
8. 关闭日志文件句柄
9. 清理 run/runtime.json
```

#### 4.3 端口动态分配

```go
func getFreePort(preferred int) int {
    // 1. 尝试首选端口
    ln, err := net.Listen("tcp", "127.0.0.1:{preferred}")
    // 2. 若占用，使用 :0 让 OS 分配随机端口
    ln, err := net.Listen("tcp", "127.0.0.1:0")
    return addr.Port
}
```

Gateway 端口优先级：用户指定端口 > 9000（默认）> 操作系统随机分配（冲突时自动换至多 8 次重试）。

### 6. 两种可执行形态

| 可执行文件 | 形态 | 技术栈 | 运行时依赖 |
|-----------|------|--------|-----------|
| `FPlayerFFService.exe` | UI 管理模式 | Electron + Chromium + Node.js | 自带 Chromium 运行时 |
| `FPlayerFFServiceKernel.exe` | 命令行模式 | Go 编译的独立可执行文件 | 无运行时依赖 |

两种形态共享同一套 ZLMediaKit 和 Gateway，仅在上层管理界面不同。
