# 主流流媒体协议介绍

## 1. RTMP

RTMP（Real-Time Messaging Protocol）是 Adobe 公司于 2005 年前后推出的私有协议，最初为 Flash Player 与 Flash Media Server 之间的音视频数据传输而设计。尽管 Flash 已于 2020 年停止支持，RTMP 至今仍是流媒体行业使用最广泛的推流协议，几乎所有直播平台和编码器的第一推流选择都是 RTMP。

RTMP 建立在 TCP 长连接之上，通过三次握手建立会话后，将音视频数据分割为固定大小的 Chunk 进行多路复用传输。每个 Chunk 包含一个 Chunk Header，记录所属的逻辑流 ID、时间戳和消息类型，接收端据此将不同流的 Chunk 重新组装为完整消息。一条 RTMP 连接可以同时承载音频、视频、控制指令等多个逻辑流，互不干扰。协议默认使用 1935 端口。

RTMP 的延迟通常在 1 到 3 秒之间，在局域网环境下可以稳定在 1 秒以内。延迟主要来源于 TCP 的可靠传输机制——丢包重传和拥塞控制会导致数据堆积——以及接收端的播放缓冲区。变体 RTMPS 在 TLS 之上运行 RTMP，提供加密传输；RTMPE 是 Adobe 的轻量加密版本；RTMFP 基于 UDP 并使用端到端加密。当前主流开源实现包括 Nginx-RTMP 模块和 SRS。

## 2. HTTP-FLV

HTTP-FLV 是将 FLV 封装格式的流数据通过 HTTP 协议以 Chunked Transfer Encoding 方式持续传输的技术方案。它本质上不是一种独立的新协议，而是 RTMP 流的 HTTP 适配——服务端将收到的 RTMP 流转封装为 FLV 格式后，通过一个持久的 HTTP 响应不断向客户端推送数据。

与 RTMP 相比，HTTP-FLV 的显著优势在于穿透防火墙和代理的能力。RTMP 使用 1935 端口的私有协议，企业防火墙通常会拦截；而 HTTP-FLV 走标准的 HTTP 80/443 端口，几乎不会被阻拦。浏览器端虽不能直接播放 HTTP-FLV，但可通过 MSE（Media Source Extensions）配合 flv.js 等库实现播放。延迟方面，HTTP-FLV 与 RTMP 相当，在 1 到 3 秒之间，远低于 HLS。缺点在于缺乏内置的自适应码率支持，且移动端浏览器兼容性有限。

## 3. HLS

HLS（HTTP Live Streaming）是 Apple 于 2009 年推出的流媒体协议，核心思想是将连续的直播流切分为一系列短小的 TS（MPEG-2 Transport Stream）分片文件，通过 HTTP 服务器分发，客户端按播放列表（M3U8 文件）逐个下载分片并连续播放。

HLS 的工作流程分为三个环节。服务端将推流输入（通常是 RTMP）实时切片，每个切片时长一般为 2 到 10 秒，同时更新 M3U8 播放列表文件，不断追加新的切片条目并移除过旧的条目。HTTP 服务器以普通静态文件的形式托管分片和播放列表，无需任何特殊服务器软件。客户端首先下载 M3U8 文件，解析出切片 URL 列表，按时间顺序逐个下载 TS 文件并送入播放器解码渲染。

HLS 的最大优势是兼容性。它完全基于 HTTP，与所有 Web 服务器、CDN 和缓存基础设施天然兼容；iOS 和 Android 系统级播放器原生支持 HLS；主流浏览器均可通过 HTML5 video 标签或 MSE 播放 HLS。缺点在于延迟较高，通常 5 到 15 秒，取决于切片时长和播放端缓冲策略。Apple 后续推出的低延迟 HLS（LL-HLS）通过缩短切片时长、预生成部分切片和增量播放列表等手段将延迟降低到 2 到 6 秒。

自适应码率是 HLS 的标志性能力。服务端可以同时生成多组不同码率的分片（如 1080p、720p、480p），在 Master Playlist 中列出所有变体流的地址。客户端根据当前网络状况自动切换码率，在网络变差时降级到低码率流以避免卡顿，在网络恢复时升级到高码率流以提升画质，切换过程对用户透明。

## 4. RTSP

RTSP（Real-Time Streaming Protocol）是一种应用层协议，用于建立和控制媒体会话，本身不传输媒体数据。它最早由 RealNetworks、Netscape 和哥伦比亚大学于 1998 年联合提出，广泛用于 IP 摄像头和监控系统。

RTSP 的设计类似于"媒体流的遥控器"。客户端通过 DESCRIBE 请求获取媒体流的 SDP（Session Description Protocol）描述，了解可用的媒体轨道和编码格式；通过 SETUP 为每个轨道指定传输参数（协议、端口）；通过 PLAY 开始传输，PAUSE 暂停，TEARDOWN 结束会话。媒体数据通常通过 RTP（Real-Time Transport Protocol）在独立的 UDP 端口上传输，RTCP（RTP Control Protocol）同步反馈网络质量。默认端口为 554。

RTSP 的优势在于对媒体会话的精细控制。它支持逐轨道的传输协商、多种传输模式（UDP 单播、UDP 组播、TCP 交织）以及精确的 seek 和快进操作，非常适合监控回放和点播场景。缺点在于防火墙穿透困难（UDP 端口动态协商）、浏览器无原生支持、部署复杂度高于 HTTP 协议。

## 5. WebRTC

WebRTC（Web Real-Time Communication）是 Google 主导推动的开源实时通信标准，于 2011 年发布并随后纳入 W3C 和 IETF 标准体系。它的设计目标是让浏览器之间可以直接进行音视频通话和数据传输，无需安装插件或依赖中转服务器。

WebRTC 的技术栈分为三层。第一层是媒体引擎，负责音视频的采集、编解码（强制支持 Opus 音频和 H.264 视频，可选支持 VP8/VP9/AV1）、回声消除、降噪和抖动缓冲。第二层是传输层，基于 SRTP（Secure RTP）在 UDP 之上传输加密的媒体数据，通过 SCTP（Stream Control Transmission Protocol）在 DTLS 隧道中传输数据通道。第三层是信令层，WebRTC 标准有意不做规定，由应用自行实现（通常用 WebSocket 或 SIP）。

WebRTC 的核心技术贡献是 ICE（Interactive Connectivity Establishment）框架，它整合了 STUN（Session Traversal Utilities for NAT）和 TURN（Traversal Using Relays around NAT）协议来解决 NAT 穿透问题。STUN 服务器帮助客户端发现自己在公网上的映射地址，TURN 服务器在直连不可行时中转媒体数据。ICE 自动尝试所有候选路径（本地地址、反射地址、中继地址），选择最优的连接方案。

WebRTC 的超低延迟是其最大优势，通常在 500 毫秒以内，远超 RTMP 和 HLS。延迟低是因为它基于 UDP，不等待丢包重传，采用 FEC（前向纠错）和 PLC（丢包隐藏）来容忍一定比例的丢包，结合自适应抖动缓冲和带宽估计来动态调整编码参数。代价是实现复杂度高，需要部署 STUN/TURN 服务器，服务端需要处理 DTLS 握手和 SRTP 加解密，推流场景下的开源解决方案不如 RTMP 成熟。

## 6. SRT

SRT（Secure Reliable Transport）由 Haivision 公司于 2017 年开源，是一种基于 UDP 的可靠传输协议，专门为公网环境下的低延迟视频传输场景设计，解决了传统 UDP 传输的丢包和抖动问题。

SRT 在 UDP 之上实现了选择性重传（ARQ）和前向纠错（FEC），仅重传丢失的数据包而非全部数据，避免了 TCP 的队头阻塞问题。发送端持续收集 RTT（往返时间）和可用带宽，动态调整发送速率和重传策略，在丢包率和带宽剧烈波动的公网链路上也能维持稳定的视频质量。同时内置 AES-128/256 加密，保障公网传输的安全性。

SRT 的典型应用场景是远程制作和云导播。电视台将现场拍摄的视频通过互联网传回制作中心，取代昂贵的卫星和专线链路。呼叫方和监听方的连接模式支持防火墙内部的设备主动发起连接到公网服务器，简化了部署。延迟通常在几百毫秒到 2 秒之间，比 HLS 低得多，比 WebRTC 略高但更稳定可靠。SRT 在开源流媒体领域的支持日益广泛，FFmpeg、OBS Studio、VLC 均已原生集成。
