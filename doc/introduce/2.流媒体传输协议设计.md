# 流媒体传输协议设计

## 1. 协议体系概述

FPlayer 系统的流媒体传输分为**控制面协议**和**数据面协议**两个层面。控制面负责会话生命周期管理和播放地址编排，数据面负责实际音视频数据的传输与分发。两个层面在物理上可分离部署，在协议上完全解耦。

## 2. 控制面协议：Gateway HTTP API

### 2.1 设计原则

- **RESTful 风格**：使用标准 HTTP 方法（GET/POST），JSON 格式的请求与响应
- **无状态服务**：Gateway 不保持与客户端的持久连接，每次请求独立
- **幂等会话创建**：同一 app+stream 的重复创建请求返回已有会话，不产生副作用
- **CORS 开放**：允许任意来源的跨域请求，便于 Web 端和移动端接入

### 2.2 API 端点设计

#### 2.2.1 健康检查

```
GET /healthz
Response: {"status": "ok"}
```

用于启动时的就绪探测和运行时的存活监控。Gateway 启动后，启动器（kernel-console 或 Electron main process）通过轮询该端点（200ms 间隔，5s 超时）确认 Gateway 就绪。

#### 2.2.2 创建流会话

```
POST /api/v1/streams/start
Content-Type: application/json

Request:
{
    "app": "live",                  // 应用名，默认 "live"
    "stream": "stream001",          // 流名，默认 "stream001"
    "serviceMode": "httpflv",       // 服务模式: direct|broadcast|httpflv
    "publisherMeta": {},            // 发布者元信息（可选）
    "sourceMeta": {},               // 来源元信息（可选）
    "publicProxyEnabled": false,    // 是否启用公网代理（可选）
    "publicHost": ""                // 公网代理地址（可选）
}

Response:
{
    "id": "a1b2c3d4e5f6g7h8",      // 会话唯一 ID（16字符 hex）
    "app": "live",
    "stream": "stream001",
    "serviceMode": "httpflv",
    "publishRtmp": "rtmp://192.168.1.100:1935/live/stream001",
    "playHttpFlv": "http://192.168.1.100:8080/live/stream001.flv",
    "playHls": "http://192.168.1.100:8080/live/stream001/hls.m3u8",
    "playUrls": {
        "rtmp": "rtmp://192.168.1.100:1935/live/stream001",
        "httpFlv": "http://192.168.1.100:8080/live/stream001.flv",
        "hls": "http://192.168.1.100:8080/live/stream001/hls.m3u8"
    }
}
```

**幂等性保证**：在创建新会话前，先遍历现有会话，若存在同 app+stream 且状态为 running 的记录，则直接返回该记录的地址信息，不创建新记录。

**会话 ID 生成**：使用 `crypto/rand` 生成 8 字节随机数，编码为 16 字符十六进制字符串。

#### 2.2.3 查询流状态

```
GET /api/v1/streams/{id}/status

Response:
{
    "id": "a1b2c3d4e5f6g7h8",
    "app": "live",
    "stream": "stream001",
    "serviceMode": "httpflv",
    "status": "running",            // running | stopped
    "publishRtmp": "rtmp://...",
    "playHttpFlv": "http://...",
    "playHls": "http://...",
    "playUrls": { ... },
    "publisherMeta": {},
    "sourceMeta": {}
}
```

#### 2.2.4 停止流

```
POST /api/v1/streams/{id}/stop

Response:
{
    "id": "a1b2c3d4e5f6g7h8",
    "status": "stopped"
}
```

停止操作仅将会话状态标记为 stopped，不删除记录，保留历史查询能力。

#### 2.2.5 列出所有流

```
GET /api/v1/streams

Response:
{
    "items": [ ... ]                // streamRecord 数组
}
```

#### 2.2.6 地址解析（移动端专用）

```
GET /api/v1/streams/resolve?app=live&stream=stream001

Response: 同 status 响应结构
```

该端点专为移动端设计。移动端仅需知道 app 和 stream 名称，无需知晓会话 ID，即可获取播放地址。内部实现为：遍历所有会话，匹配 app+stream，返回最新创建的匹配记录。

### 2.3 三种服务模式

Gateway 支持三种服务模式（`serviceMode`），决定生成的播放地址集合：

| 模式 | 值 | 生成的 URL | 说明 |
|------|-----|-----------|------|
| 直连 | `direct` | 仅 RTMP | 占位模式，不生成 HTTP-FLV/HLS 地址 |
| 广播分发 | `broadcast` | RTMP + HTTP-FLV + HLS | 支持全协议分发 |
| HTTP-FLV 转换 | `httpflv` | RTMP + HTTP-FLV + HLS | 侧重 HTTP-FLV 输出 |

### 2.4 地址生成策略

Gateway 从环境变量读取 ZLMediaKit 的运行时端口：
- `ZLM_RTMP_PORT`（默认 1935）
- `ZLM_HTTP_PORT`（默认 8080）

播放地址的 host 部分由**主机选择策略**决定：

1. **公网代理模式**（最高优先级）：若启用了 `publicProxyEnabled` 且 `publicHost` 非空，使用公网地址
2. **启动时选定地址**：启动阶段通过网卡可达性探测选定的 IP
3. **请求级动态选择**（Linux）：根据客户端 IP 进行路由优选、同子网匹配、轮询可达性探测
4. **回退策略**：使用请求的 Host 头或 `X-Forwarded-For` 头，最终回退到 `localIPv4()`

### 2.5 主机选择算法（Linux）

Linux 环境下，由于多网卡场景普遍，Gateway 实现了多层级的主机选择策略：

**第一层：路由优选**。通过 UDP 拨号到客户端 IP 的 53 端口，获取操作系统路由表为该目标选择的本地接口地址。该地址与客户端在同一路由路径上，可达性最优。

**第二层：同子网匹配**。遍历所有本地 IPv4 候选地址，筛选与客户端 IP 处于同一 /24 子网的地址，对候选地址进行 TCP 可达性探测（gateway 端口 + RTMP 端口，300ms 超时）。

**第三层：轮询可达**。若以上策略均未找到合适地址，对所有候选地址进行轮询 TCP 可达性探测。

**地址过滤**：排除回环地址（127.0.0.0/8）、链路本地地址（169.254.0.0/16）、非活跃网卡地址。

## 3. 数据面协议：流媒体传输

### 3.1 协议栈

```
┌──────────────────────────────────────┐
│            应用层                      │
│  桌面客户端 (推流)  │  移动端 (拉流)     │
├──────────────────────────────────────┤
│          封装/传输层                   │
│  RTMP │ HTTP-FLV │ HLS │ RTSP        │
├──────────────────────────────────────┤
│            编码层                      │
│     H.264 / H.265 (视频)              │
│     AAC / MP3 (音频)                  │
├──────────────────────────────────────┤
│            传输层                      │
│         TCP / HTTP                    │
└──────────────────────────────────────┘
```

### 3.2 RTMP（Real-Time Messaging Protocol）

**用途**：推流的主要协议，也支持拉流播放。

**技术实现**：
- **推流侧**（桌面客户端）：StreamFFmpeg 使用 FFmpeg libavformat 的 RTMP 输出模块，通过 `avformat_write_header` + `av_write_frame` + `av_interleaved_write_frame` 将编码后的音视频帧推送到 ZLMediaKit
- **分发侧**（服务端）：ZLMediaKit 作为 RTMP 服务器接收推流，同时可作为 RTMP 源站对外提供拉流
- **拉流侧**（移动端）：media_kit 底层 libmpv 支持 RTMP 拉流播放

**地址格式**：`rtmp://{host}:{port}/{app}/{stream}`

**延迟特征**：端到端延迟通常为 1-3 秒，适合对延迟有要求的实时场景。

### 3.3 HTTP-FLV（HTTP Flash Video）

**用途**：低延迟拉流播放，是系统中延迟最低的 HTTP 拉流协议。

**技术实现**：
- ZLMediaKit 将 RTMP 流实时转封装为 FLV 格式，通过 HTTP chunked 传输持续输出
- 客户端建立 HTTP 长连接，持续接收 FLV tag 数据并解码播放
- 移动端通过 media_kit 的 HTTP-FLV 支持进行播放

**地址格式**：`http://{host}:{port}/{app}/{stream}.flv`

**延迟特征**：端到端延迟通常为 1-3 秒，与 RTMP 相当，但穿透防火墙和代理的能力优于 RTMP。

### 3.4 HLS（HTTP Live Streaming）

**用途**：兼容性最好的拉流协议，适合 Web 端和不支持 RTMP/FLV 的环境。

**技术实现**：
- ZLMediaKit 将 RTMP 流切片为 TS 分片文件，生成 M3U8 播放列表
- 客户端通过标准 HTTP GET 请求获取 M3U8 和 TS 分片
- 移动端 Web 模式下优先使用 HLS，Android 端 FLV/RTMP 兼容性不佳时回退到 HLS

**地址格式**：`http://{host}:{port}/{app}/{stream}/hls.m3u8`

**延迟特征**：端到端延迟通常为 5-15 秒（取决于分片时长设置），延迟较高但兼容性最好。

### 3.5 RTSP（Real-Time Streaming Protocol）

**用途**：可选协议，仅在 Linux 环境下启用，用于兼容传统监控摄像头等设备。

**技术实现**：
- ZLMediaKit 支持 RTSP 推流和拉流
- 仅在 Linux 版本中动态分配 RTSP 端口（默认优先 8554）

## 4. 桌面客户端推流路由协议

桌面客户端在推流时使用自定义的 URL Scheme 来指定输入来源和处理方式。StreamFFmpeg 通过解析输入 URL 的前缀来确定推流策略：

| 前缀 | 含义 | 处理方式 |
|------|------|---------|
| `__compose_scene__:` | 多源合成场景 | 从多个 ScreenFrameBus/CameraFrameBus 通道读取帧，YUV 合成后编码推流 |
| `__screen_capture__:` | 屏幕直接捕获 | 独立启动屏幕捕获，编码后推流 |
| `__screen_preview__:` | 屏幕预览帧 | 从 ScreenFrameBus 读取预览帧，编码后推流 |
| `__camera_capture__:` | 摄像头直接捕获 | 独立启动摄像头捕获，编码后推流 |
| `__camera_preview__:` | 摄像头预览帧 | 从 CameraFrameBus 读取预览帧，编码后推流 |
| `__file_transcode__:` | 文件转码 | 解码本地文件并重新编码到目标码率/分辨率后推流 |
| `__file_preview__:` | 文件预览帧 | 从播放器的 ScreenFrameBus 读取帧，编码后推流 |
| 无前缀（文件路径） | 文件流拷贝 | 使用 avformat 的 remux 模式，不解码不重新编码，直接流拷贝推流 |

这种设计将多个推流策略统一在一个接口下（`IStream::startPush(inputUrl, outputUrl)`），通过 URL Scheme 路由到不同的处理循环，保持了 API 的简洁性。

## 5. 帧总线（Frame Bus）设计

帧总线是桌面客户端内部用于在生产者和消费者之间传递 YUV 帧数据的线程安全通道。

### 5.1 ScreenFrameBus

屏幕帧总线，用于连接屏幕捕获后端和推流编码线程：

- **多通道设计**：通过 `sourceId` 区分不同的捕获源（多屏幕、多窗口）
- **序列号机制**：每帧携带递增序列号，消费者通过 `snapshotIfNew(serial)` 避免重复处理
- **目标尺寸协商**：生产者可发布 `publishTargetSize()` 通知推流目标分辨率，采集端据此调整输出
- **线程安全**：使用 QMutex 保护内部数据，支持多生产者多消费者

### 5.2 CameraFrameBus

摄像头帧总线，功能与 ScreenFrameBus 类似，但更简单（无需目标尺寸协商）。用于将摄像头预览帧传递给推流编码线程。

### 5.3 数据流路径

```
屏幕捕获线程 / 摄像头捕获线程
        │
        ▼ YUV420P 帧
  ScreenFrameBus / CameraFrameBus
        │
        ▼ snapshotIfNew()
  推流编码线程 (pushScreenPreviewLoop / pushCameraPreviewLoop)
        │
        ▼ H.264/H.265 编码帧
  av_interleaved_write_frame()
        │
        ▼ RTMP 协议
  ZLMediaKit 服务端
```

## 6. 视频编码配置

### 6.1 编码器选择策略

StreamFFmpeg 在启动时自动探测可用的硬件编码器，优先级从高到低：

1. **h264_nvenc** — NVIDIA GPU 硬件编码
2. **h264_amf** — AMD GPU 硬件编码
3. **h264_qsv** — Intel Quick Sync 硬件编码
4. **libx264** — 软件编码（通用回退）

同时探测 D3D11VA 硬件设备（`av_hwdevice_ctx_create(AV_HWDEVICE_TYPE_D3D11VA)`）用于 GPU 加速的像素格式转换。

### 6.2 码率估算

系统根据目标分辨率和帧率自动估算合适的视频码率。`estimateBitrateKbps()` 函数基于分辨率像素数和帧率计算推荐码率，平衡画质和带宽占用。

## 7. 音频处理管线

### 7.1 音频采集

桌面客户端支持多路音频输入：
- **输入采集**：通过 WASAPI Loopback（Windows）采集系统音频输出或麦克风输入
- **音频监控**：推流时可同时监听音频

### 7.2 音频管道

StreamFFmpeg 内部维护独立的音频处理管线（`audio_pipeline.h`）：
- Planar 格式的音频混音
- FIFO 缓冲确保音视频同步
- swresample 重采样到目标采样率和声道布局
- 音频帧与视频帧交错写入（`av_interleaved_write_frame`）保证同步

## 8. 协议选择建议

| 场景 | 推荐协议 | 原因 |
|------|---------|------|
| 推流（桌面端→服务端） | RTMP | 成熟稳定，编码器原生支持，低延迟 |
| 拉流-桌面端 | HTTP-FLV | 低延迟，HTTP 穿透性好 |
| 拉流-Android 原生 | HLS | 兼容性最佳，Android 对 FLV 支持有限 |
| 拉流-Web 浏览器 | HLS | 浏览器原生支持（通过 hls.js 或原生 HLS） |
| 拉流-局域网低延迟 | RTMP | 延迟最低，适合实时监控 |
| 拉流-公网弱网 | HLS | 自适应码率，CDN 友好 |
