# ZLMediaKit 音视频与流媒体处理技术介绍

ZLMediaKit 是一个轻量级、高性能的 C++ 流媒体服务器内核，由国内开发者社区主导维护，以 MIT 许可证开源。它的核心理念是实现一套覆盖主流流媒体协议、零外部依赖、可嵌入的流媒体处理引擎，既可作为独立服务器部署，也可作为 SDK 嵌入到宿主应用中。

ZLMediaKit 的架构基石是事件驱动模型。在 Linux 上基于 epoll 实现，在 Windows 上基于 IOCP 实现，两种模型都采用了 Reactor 模式——主事件循环监听所有网络事件，事件就绪后通过回调分发到对应的协议处理器。这种设计使得单进程可以高效管理数千个并发连接，CPU 占用和线程数不受连接数线性增长的拖累。网络层自行管理 Socket 的异步读写和缓冲区，不与任何第三方网络框架耦合。

协议支持是 ZLMediaKit 最突出的能力。在推流侧，它支持 RTMP、RTSP 和 RTP over UDP/TCP 三种输入方式，意味着摄像头、编码器、OBS 等主流推流工具都可以直接接入。在拉流侧，它支持 RTMP、RTSP、HTTP-FLV、WebSocket-FLV、HLS 和 WebRTC 六种输出方式，覆盖从低延迟到高兼容性的全场景需求。其中 HTTP-FLV 和 WebSocket-FLV 是实时转封装输出——服务端接收到 RTMP 推流后，不解码、不重编码，仅将 RTMP 数据包重新组装为 FLV 格式的 Tag，通过 HTTP Chunked 或 WebSocket 持续推送。HLS 则是将输入流实时切片为 TS 文件并生成 M3U8 播放列表，切片时长和保留数量均可配置，兼顾延迟和兼容性。WebRTC 的支持基于 WHIP/WHEP 标准信令协议，结合内置的 STUN 能力和可选的 TURN 中转，能够将传统 RTMP 流桥接到浏览器端的超低延迟播放，延迟通常低于 500 毫秒。

媒体处理管线是 ZLMediaKit 内部的核心数据路径。当一路 RTMP 流推入后，数据首先进入解封装器，解析出 H.264/H.265 视频轨道和 AAC/Opus 音频轨道。解封装后的原始码流分两条路径处理：一条路径写入录制文件（支持 MP4、FLV、TS 等多种封装格式），另一条路径进入多协议分发器。分发器根据当前有哪些客户端订阅了该流，为每个订阅的协议创建对应的输出通道——HTTP-FLV 通道持续输出 FLV Tag，HLS 通道定时写入 TS 分片，RTMP 通道将数据重新封装为 RTMP Chunk 发送给拉流端。整个过程不涉及解码和重编码，只是封装格式的转换，CPU 消耗极低，单机可支持上千路并发。

按需拉起是 ZLMediaKit 的一个重要设计。默认配置下，服务端不会为无人观看的流启动 HLS 切片或 WebRTC 转码，只有当第一个客户端请求对应协议的播放地址时，才为该流开启对应的分发通道。观众断开后，通道在可配置的延迟后自动关闭。这个机制避免了无人观看的流持续消耗磁盘 IO 和 CPU 资源。

ZLMediaKit 的模块之间通过松耦合的方式协作。协议解析、媒体封装、网络传输、录制管理等模块各自独立，通过内部的事件总线和数据缓冲区交换信息。这种设计使得模块可以独立测试和替换，也为二次开发提供了清晰的扩展点。例如要增加一个新的输出协议，只需要实现对应的分发通道模块并注册到分发器，不需要修改其他模块。

性能方面，ZLMediaKit 在主流 x86 服务器上可以轻松承载数千路 RTMP 并发推拉流，内存占用通常控制在几百兆以内。低延迟特性得益于其设计中对缓冲策略的精细控制——内部流转发无额外缓冲，输出端默认零缓冲发送（可配置），HLS 切片时长最短支持 1 秒。这些参数使得 ZLMediaKit 在各种部署环境——从树莓派到云服务器——都能找到合适的配置策略。

ZLMediaKit 的生态也在持续扩展。社区提供了多种语言的 SDK 和 RESTful API 封装，支持通过 HTTP Hook 回调通知流的上下线事件，支持 MP4 录像回放和按需点播，还提供了 C API 接口方便集成到 C++ 以外的项目中。
