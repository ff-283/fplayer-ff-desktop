# 系统测试报告

## 1. 测试环境介绍

### 1.1 硬件环境

测试使用三台设备组成局域网环境，通过同一路由器下的千兆以太网和 Wi-Fi 6 连接。服务端部署在一台配备 Intel i7-13700H 处理器、32GB 内存和 NVIDIA RTX 4060 显卡的 Windows 11 笔记本上，同时承担推流任务。桌面拉流端使用另一台配备 AMD Ryzen 7 5800H、16GB 内存的 Windows 10 笔记本。移动端使用小米 14（骁龙 8 Gen 3、Android 14）在 5GHz Wi-Fi 下接入。

### 1.2 软件环境

服务端运行 fplayer-ff-service 的 portable-kernel 发布包，内置 ZLMediaKit（预编译二进制）和 Go Gateway。桌面端和拉流端均运行 fplayer-ff-desktop 的 MSVC Release 构建，基于 Qt 6.10.2 和 FFmpeg 8.1。移动端安装 fplayer-ff-mobile 的 release APK，基于 Flutter 3.x 和 media_kit（libmpv）。所有设备通过千兆交换机互联，服务端防火墙已放行 Gateway（9000）、RTMP（1935）和 HTTP-FLV（8080）端口。

---

## 2. 测试性能指标

测试围绕六类指标展开。

端到端延迟是核心指标，指从桌面端采集画面到拉流端显示出画面的时间差。测试采用屏幕时间码对比法，推流端全屏显示毫秒级计时器，拉流端截图后人工对比时间码差值。HTTP-FLV 链路目标延迟不超过两秒，HLS 链路放宽到八秒。吞吐量方面，验证服务端至少承载五十路并发推流，单路流支撑不少于一百个并发拉流。资源占用测试重点关注服务端空闲内存（目标不超过五百兆）和桌面端硬编推流时的 CPU 占用（目标不超过百分之三十）。画质测试验证 1080p@30fps 推流在四到六 Mbps 码率下的主观画质和帧率保持率（不低于百分之九十五）。可靠性测试验证服务端连续运行七十二小时无崩溃重启。功能完整性测试按 MVP 范围验证全链路闭环。

---

## 3. 桌面播放端测试

### 3.1 本地文件播放

测试使用多个不同编码格式的视频文件验证播放器兼容性和性能。H.264+AAC 编码的 1080p MP4 文件打开后播放流畅，进度条拖拽跳转无明显延迟，音视频同步准确。HEVC 编码的 4K MKV 文件在软解码时 CPU 占用约 45%，帧率保持约 28fps 有轻微掉帧，属于预期行为。FLV 格式文件正常播放。播放器音量调节、暂停/恢复、倍速播放（0.5x/1.5x/2.0x）均正常响应。循环播放模式在文件末尾正确回到开头。测试覆盖了约十个不同编码和分辨率的文件，整体兼容性良好。

### 3.2 摄像头采集与推流

USB 摄像头（罗技 C920）在 FFmpeg dshow 后端下正确枚举，支持的格式列表完整展示（从 640×480@30fps 到 1920×1080@30fps）。选择 1080p@30fps 后预览画面流畅，无延迟感。以 NVENC 硬编推流到局域网 P2P 地址（rtmp://192.168.1.x/live/test），拉流端用 VLC 播放验证画面完整、音视频同步。切换编码器为 CPU（libx264）后推流正常，CPU 占用从 8% 升至 45%。切换分辨率到 720p@30fps 后推流重启正常，画质和流畅度均合格。虚拟摄像头（OBS Virtual Camera）也能被正确枚举和使用。

### 3.3 屏幕捕获与推流

DXGI 后端整屏捕获 1920×1080 显示器，采集流畅度测试中快速拖动窗口和播放视频源，拉流端无明显撕裂或卡顿。窗口模式下选择特定窗口进行捕获，只捕获该窗口内容，其他窗口遮挡时捕获内容不受影响（DXGI 特性）。帧率设置为 30fps 时实际帧率在 29-31fps 之间波动，帧率保持率约 97%，达标。开启光标捕获后，拉流端能看到光标移动，光标位置与实际位置偏差很小。DXGI 设备丢失恢复测试通过，在休眠唤醒和切换显示器后自动恢复采集。

### 3.4 拉流播放

从服务端拉取 HTTP-FLV 流，输入 Gateway 地址和 app/stream 后点击解析地址，成功获取播放 URL 并开始播放。画面延迟约 1.5 秒，在目标范围内。拉流过程中切换全屏正常。服务端停止推流后拉流端约 3 秒内显示连接断开。P2P 直拉模式下输入完整 RTMP 地址后播放正常。

## 4. 三端联调测试

### 4.1 基本三端链路

桌面端（推流端）以摄像头 1080p@30fps 通过服务端模式推流，Gateway API 创建会话成功后获取 publishRtmp 地址并开始推流。桌面端（拉流端）在同一局域网另一台机器上通过服务端模式解析播放地址后开始拉流，HTTP-FLV 协议下画面延迟约 1.5 秒。移动端输入 Gateway URL 和 app/stream 后以 HLS 协议播放，视频正常显示，HLS 切片机制下延迟约 5-7 秒，符合预期。三端链路完整：桌面采集→服务端分发→桌面+移动同时拉流，全部正常。

### 4.2 服务端会话管理

通过 curl 直接测试 Gateway API。连续十次 POST /api/v1/streams/start 使用相同的 app+stream 参数，第一次返回 200 并创建会话，后续九次均返回 200 且 streamId 相同，验证幂等性正确。使用不同 app+stream 创建第二个流，两个流并发存在，GET /api/v1/streams 返回两个会话。停止第一个流后再次创建同名流，返回新的 streamId，说明旧会话已释放。健康检查 /healthz 始终返回 ok。端口冲突场景下，先启动一个占用 9000 端口的进程，Gateway 自动切换到其他端口并成功启动。

### 4.3 屏幕推流 + 移动端 HLS 播放

桌面端以屏幕捕获模式推流（DXGI，1080p@30fps，HTTP-FLV 分发模式），移动端选择 HLS 协议播放。桌面端在屏幕上来回拖动窗口和播放视频，移动端画面跟随变化，延迟约 5-8 秒（HLS 正常范围）。移动端切换到 HTTP-FLV 协议后延迟降至约 2 秒，但 Android 端 FLV 播放偶有缓冲，不如 HLS 稳定。

### 4.4 多源合成推流联调

桌面端在组合模式下添加摄像头和屏幕两个素材，调整位置和大小后以 1920×1080 输出推流。移动端拉流播放，画面同时包含两个源的合成内容，布局比例与推流端预览一致。切换素材 Z 顺序后拉流画面同步变化。

### 4.5 公网 FRP 代理联调

服务端部署在内网机器，通过 FRP 将 Gateway（9000）、RTMP（1935）和 HTTP（8080）端口映射到公网服务器。配置 SERVICE_PUBLIC_HOST 为公网 IP 后，API 返回的播放地址已替换为公网地址。从公网环境访问 Gateway 创建会话并拉流成功，延迟略有增加（约 2-3 秒）。

### 4.6 稳定性测试

服务端连续运行六小时后，Gateway API 响应正常，各端口监听正常，内存占用稳定在约 120MB（空闲时约 80MB，含两路推流后约 120MB）。连续推流两小时后未出现画面花屏、绿屏或断连。移动端播放四十分钟后因 Android 系统省电策略暂停，回到前台后自动恢复播放。

### 4.7 异常恢复测试

在推流过程中强制终止 ZLMediaKit 进程，Gateway 的健康检查仍正常但会话中的推流信息变为不可用状态。桌面端推流检测到连接断开后显示错误信息，点击停止流后重新启动可以恢复正常推流。重启 Gateway 进程后（端口不变），此前创建的会话数据丢失（内存存储特性），桌面端重新调用创建会话 API 可以正常重建。

## 5. 小结

本次系统测试覆盖了桌面端的本地播放、摄像头采集推流、屏幕捕获推流和拉流播放功能，以及三端（桌面推流端、桌面拉流端、移动端）的协同链路。核心测试结果如下。

延迟表现方面，HTTP-FLV 链路端到端延迟约 1.5 秒，HLS 链路约 5-8 秒，均在设计目标范围内。NVENC 硬件编码推流时桌面端 CPU 占用约 8%，资源消耗低；软件编码时 CPU 占用上升至约 45%，仍在可接受范围。服务端内存占用约 120MB（含两路推流），远低于 500MB 上限。

功能完整性方面，MVP 范围内的所有功能模块均通过验证：多种输入源的采集和推流、P2P 直连和服务端两种推流模式、HTTP-FLV 和 HLS 双协议拉流、多源合成推流、会话管理的幂等性和 CRUD 操作、端口冲突自动恢复。公网 FRP 代理场景也通过了联调验证。

存在问题方面，Android 端 HTTP-FLV 播放偶有缓冲，建议移动端默认选择 HLS 以获得更稳定的播放体验；Gateway 重启后会话数据丢失是已知的内存存储特性，后续版本规划中已列入 Redis 持久化改进；连续运行测试仅进行六小时而非七十二小时目标，后续需补足超长时间稳定性验证。
