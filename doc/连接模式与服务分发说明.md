# 连接模式与服务分发说明

本文用于向最终用户解释两种使用方式：直连模式与服务分发模式。

## 1. 模式概览

### 模式 A：直连模式（不经过服务端）

- 适用场景：一对一、局域网临时连线、快速调试。
- 工作方式：推流端直接推送到目标地址，拉流端直接从该地址拉流。
- 优点：链路最短、配置最少、延迟低。

### 模式 B：服务分发模式（经过服务端）

- 适用场景：一对多、多对多、跨端兼容、后续扩展广播与协议转换。
- 工作方式：推流前先向服务端创建会话，桌面端拿到服务端返回的 RTMP 地址后再发流。
- 服务端能力：统一分发、协议转换（例如 RTMP -> HTTP-FLV）、会话管理。

## 2. 推流端操作步骤

1. 打开 `推拉流 -> 推流`。
2. 如果是直连，按原方式填写协议模板与输出地址。
3. 如果是服务分发：
   - 勾选 `推送到服务端（由服务端分发/转协议）`
   - 填写 `服务地址`、`服务 app`、`服务 stream`
   - 其中 `服务地址` 以 service 端 `run/runtime.json` 的 `gateway.url` 为准
   - 选择 `服务类型`（广播分发 / HTTP-FLV 转换）
4. 点击 `开始推流`。

推流前，桌面端会向服务端发送会话创建请求，并携带元信息（场景类型、编码参数、推流端 IP 等）。  
服务端返回 RTMP 推流地址后，桌面端自动使用该地址发流。

## 3. 拉流端如何获取地址

服务分发模式下，拉流端不再依赖“推流端本机地址”，而是使用服务端提供的播放入口：

- RTMP 地址（可用于部分播放器）
- HTTP-FLV 地址（用于仅支持 HTTP-FLV 的端）

其中 HTTP-FLV 地址会在推流配置窗口的 `HTTP-FLV` 字段中显示。

此外，拉流监视窗口支持直接输入 `streamId` 自动解析地址：

1. 勾选 `从服务端按 streamId 自动解析拉流地址`
2. 填写 `服务地址` 与 `streamId`
3. 选择优先协议（HTTP-FLV / RTMP）
4. 点击 `解析地址` 或直接 `开始拉流`

> 建议：先确认 service UI 状态为“服务已就绪”，再在 desktop 发起推流/拉流解析，避免出现 `Failed to fetch`。

## 4. 两种模式如何选择

- **只是一对一且同网段**：优先直连模式。
- **多人观看或协议兼容要求高**：优先服务分发模式。

## 5. 服务类型说明

- `广播分发`：服务端以分发为主，供多个观看端同时拉流。
- `HTTP-FLV 转换`：服务端重点提供 HTTP-FLV 输出，适配只支持 HTTP-FLV 的拉流端。

> 说明：两种服务类型都由服务端统一管理会话，后续可继续扩展鉴权、录制、统计等能力。

## 6. 常见错误（服务分发）

### 6.1 `Failed to fetch`

常见原因：

- service 尚未完成启动（UI 仍在“启动中”）
- desktop 填写了固定 `:9000`，但 service 实际端口已动态变化
- `gateway.url` 不可达或防火墙拦截

建议处理：

1. 打开 service 目录下 `run/runtime.json`
2. 复制 `gateway.url` 到 desktop 的“服务地址”
3. 检查 service 日志：`logs/gateway.err.log`
