## 二、详细分析

### P1 — DXGI 屏幕采集双路 BGRA→YUV 转换合并

**文件**：[screencapturedxgi.cpp](backend/desktopcapture_dxgi/src/screencapturedxgi.cpp) `captureOneFrame()`

**现状**：
- 每帧采集后，从 GPU staging texture 逐行 memcpy 到 CPU 内存
- 对同一帧 BGRA 数据执行**两次** `sws_scale()`：一次转预览 YUV，一次转推流 YUV（可能不同分辨率）
- 当推流尺寸与预览尺寸相同时（`captureOneFrame` 760行），代码已做复用；但当尺寸不同时，BGRA 源被完整缩放两次

**阻塞点**：
1. `sws_scale` 是 CPU 密集型操作，4K 分辨率下每次缩放约 2-8ms
2. 两次 `sws_scale` 串行执行 = 双倍 CPU 时间
3. GPU→CPU memcpy（逐行）也是瓶颈，RowPitch 很大时尤其明显

**优化方案**：
- **短期**：使用 `SWS_FAST_BILINEAR` 替代 `SWS_BILINEAR`，在画质可接受的前提下加速缩放
- **中期**：推流尺寸 ≤ 预览尺寸时，先缩放到推流尺寸发布，预览利用 OpenGL 硬件缩放（已有 shader），只需一次 `sws_scale`
- **长期**：考虑使用 D3D11 Video Processor 在 GPU 上完成色彩空间转换和缩放，完全避免 CPU `sws_scale`

**预估提升**：CPU 采集线程负载降低 30-40%（4K 场景）

### P2 — 帧数据总线零拷贝改造

**文件**：
- [screenframebus.h](common/include/fplayer/common/screenframebus/screenframebus.h)
- [screenframebus.cpp](common/src/screenframebus.cpp)
- [cameraframebus.cpp](common/src/cameraframebus.cpp)

**现状**：
- `ScreenFrame::y/u/v` 是 `QByteArray`，`publish()` 时做深拷贝（隐式共享在跨线程场景下会触发 detach）
- `dispatchFrameToView()` 再显式构造新的 `QByteArray` 副本（见 `screencaptureffmpeg.cpp:277-279`）
- `FGLWidget::updateYUVFrame()` 再次赋值 `QByteArray`（隐式共享引用计数）
- 最终一帧 YUV 数据在传递链路中被复制 2-3 次

**阻塞点**：
- 1080p YUV420P 每帧约 3MB，4K 约 12MB — 每帧分配+拷贝+释放 2-3 次
- 30fps × 12MB × 3 = 约 1GB/s 的内存带宽消耗
- `QHash<QString, Channel>` 以 QString 做 key，每帧 hash 查找

**优化方案**：
- **核心方案**：引入预分配环形缓冲区（ring buffer），帧数据写入固定槽位，消费者读取同一块内存
- 使用 `std::shared_ptr<uint8_t[]>` + `std::atomic<size_t>` 序列号实现无锁单写多读
- 将 `Channel` 的 key 类型从 `QString` 改为 `int` 枚举或固定大小的 `char[32]`
- 或使用 `std::array<uint8_t>` 替代 `QByteArray`，避免隐式共享开销

**预估提升**：帧传递延迟降低 20-30%，内存分配压力显著减少

### P3 — OpenGL 纹理上传优化（PBO 异步上传）

**文件**：[fglwidget.cpp](common/src/fglwidget.cpp) `paintGL()` / `updateYUVTextures()`

**现状**：
- `paintGL()` 中持有 mutex 复制 `YUVData`（包含 3 个 QByteArray 的引用计数递增）
- `updateYUVTextures()` 同步调用 `glTexSubImage2D()` — CPU 等待 GPU 完成数据拷贝
- 每帧上传三张纹理（Y + U + V），4K 时 Y 平面就 8MB

**阻塞点**：
- `glTexSubImage2D` 是同步操作，CPU 在等待 GPU DMA 完成期间阻塞
- mutex 持锁期间包含整个数据复制和纹理上传，阻塞帧生产者线程

**优化方案**：
- 使用 PBO（Pixel Buffer Object）实现异步纹理上传：双缓冲 PBO，一帧 GPU 在 DMA 传输时，CPU 填充另一个
- 或者使用 `glTexStorage2D` + `glTexSubImage2D` 配合 fence sync object 做流水线
- 将 mutex 锁粒度缩小：仅复制指针/引用，纹理上传在锁外完成

**预估提升**：渲染帧率提升 15-25%，UI 线程卡顿减少

### P4 — 推流编码管线并行化

**文件**：[streamffmpeg.cpp](backend/stream_ffmpeg/src/streamffmpeg.cpp) `pushScreenLoop()` / `pushCameraLoop()` 等

**现状**：
- 推流循环中，帧采集、编码、封装全部在**同一个线程**内串行执行
- 采集线程从 ScreenFrameBus 取帧 → sws_scale 缩放 → avcodec_send_frame → avcodec_receive_packet → av_interleaved_write_frame
- 编码器（尤其是软件编码）是最大瓶颈，但采集和封装在等待

**阻塞点**：
- 编码延迟（尤其是软件 H.264）阻塞整个管线
- 单线程无法利用多核 CPU
- mux 写入被编码阻塞，网络发送也可能在编码期间空闲

**优化方案**：
- **采集→编码队列→封装三阶段流水线**：
  - 线程1：采集+缩放，产出 AVFrame 放入有界队列
  - 线程2：编码，从队列取 AVFrame，产出 AVPacket 放入输出队列
  - 线程3：封装+网络写入，从输出队列取 AVPacket 发送
- 队列使用 `std::condition_variable` 实现背压
- 硬件编码器（NVENC/AMF）场景下，编码几乎不占 CPU，但异步发送 AVPacket 仍能减少关键路径

**预估提升**：推流吞吐提升 20-35%，编码延迟抖动减少

### P5 — 内存池与预分配

**文件**：涉及多个模块

**现状**：
- 每帧在 `captureOneFrame()` 中检查 `m_bgraFrame`、`m_previewY/U/V`、`m_pushY/U/V` 大小并 `resize()`，大部分帧命中大小不变，但仍有分支和容量检查开销
- `remuxLoop()` / `pushScreenLoop()` 等函数中 `AVFrame*` / `AVPacket*` 每次循环 `av_frame_alloc` / `av_packet_alloc`（虽然通常只分配一次）
- `pushScreenLoop()` 中编码器用 `av_frame_alloc()` 分配输入帧，每帧都要

**阻塞点**：
- 频繁 `QByteArray::resize()` 可能导致内存碎片
- AVFrame/AVPacket 分配虽然是 FFmpeg 内部池化过，但跨函数边界仍存在分配

**优化方案**：
- 在初始化阶段预分配所有帧缓冲区，运行时仅更新指针/大小
- 使用 `std::vector<uint8_t>` + `reserve()` 替代 `QByteArray::resize()`
- 对 YUV 平面使用固定预分配大缓冲 + offset 管理，避免 per-frame realloc
- 为 AVFrame/AVPacket 创建对象池（循环复用）

**预估提升**：减少 10-20% 内存分配开销，降低碎片化

### P6 — 拉流预览解码线程分离

**文件**：[streamffmpeg.cpp](backend/stream_ffmpeg/src/streamffmpeg.cpp) `remuxLoop()`

**现状**：
- `remuxLoop` 的单线程内同时做：网络读取（`av_read_frame`）、预览视频解码（`avcodec_send_packet`/`receive_frame`）、预览音频解码+重采样+QAudioSink 播放、录制写入、推流转发
- 预览解码（尤其是软件解码 H.264/H.265）消耗 CPU，阻塞了主循环的 `av_read_frame` 和 `av_write_frame`

**阻塞点**：
- 软件视频解码 1080p 约 3-10ms/帧，阻塞整个拉流循环
- 高码率流可能导致缓冲溢出或丢帧

**优化方案**：
- 将预览解码移到独立线程：主循环读取 packet 后浅拷贝投递到解码线程，主循环继续转发
- 解码线程产出 YUV 帧后发布到 ScreenFrameBus
- 如果拉流仅做转发（不需要预览），可完全跳过解码

**预估提升**：拉流吞吐提升 15-25%，高负载下丢帧减少

### P7 — 日志系统锁争用优化

**文件**：[streamffmpeg.cpp](backend/stream_ffmpeg/src/streamffmpeg.cpp) `appendLogLine()` / FFmpeg log callback

**现状**：
- `appendLogLine()` 每调用一次就 `QMutexLocker` + `QString` 拼接操作
- 推流循环中频繁调用（编码统计、网络状态等），每次都在竞争同一把 `m_mutex`
- FFmpeg 全局 log callback 内部也有 `static std::mutex` + `vsnprintf` 2048 字节 buffer

**阻塞点**：
- 高频日志路径下锁争用
- `QString::arg()` 链式拼接在热路径上有可观的分配开销

**优化方案**：
- 使用无锁 SPSC 队列（`boost::spsc_queue` 或手写 ring buffer）替代 mutex，日志行 push 到队列，由独立线程消费
- `appendLogLine` 中用 `QStringBuilder` 或 `std::ostringstream` 减少临时 QString 分配
- FFmpeg log callback 使用 `thread_local` buffer 替代 `static` + `mutex`

**预估提升**：高日志量场景下各线程吞吐提升 5-10%

### P8 — CaptureWindow 拆分与 UI 刷新合并

**文件**：[capturewindow.cpp](widget/src/capturewindow.cpp)（219 个符号，超大类）

**现状**：
- `CaptureWindow` 是单个超大类，承载了：推流 UI、拉流 UI、屏幕采集 UI、摄像头 UI、组合模式 UI、预览管理、设置管理、AI 聊天入口、图池管理等几乎所有功能
- 多个独立 `QTimer` 用于不同 UI 刷新，未做合并/节流
- 多处 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 导致 UI 线程被大量积压事件冲击

**阻塞点**：
- 类过大，编译器优化受限（内联、LTO）
- UI 刷新缺乏统一调度，可能出现同一帧内多次 layout/paint
- `QueuedConnection` 积压可能导致事件循环响应变慢

**优化方案**：
- 按功能拆分为独立 Widget 类：PushPanel、PullPanel、PreviewPanel、ComposePanel、SettingsPanel
- 合并定时器为单一刷新循环（匹配显示器刷新率）
- 使用 `QTimer::singleShot` + 合并标记减少重复刷新
- 用 `Qt::DirectConnection` + 线程安全标记 替代非必要的 `QueuedConnection`

**预估提升**：UI 响应性显著改善，窗口 resize/拖拽更流畅

### P9 — 图池缩略图懒加载

**文件**：[imagepoolsidebar.cpp](widget/src/imagepoolsidebar.cpp)

**现状**：
- `loadImages()` 一次性加载目录下所有图片并创建缩略图 QIcon
- 目录变更时触发 `Full reload`（`onDirectoryChanged`）
- 缩略图通过 `QImageReader::setScaledSize()` 生成，在主线程执行

**阻塞点**：
- 大量图片目录（数百张）时，一次性生成所有缩略图导致 UI 冻结
- 目录变更全量重载

**优化方案**：
- 实现虚拟列表：仅生成可见项 + 前后缓冲区的缩略图
- 缩略图生成放入后台线程（`QtConcurrent::run`）
- 使用 `QFileSystemWatcher` 的增量更新替代全量重载

**预估提升**：大量图片时启动速度几秒级改善

### P10 — 摄像头设备枚举缓存

**文件**：[streamffmpeg.cpp](backend/stream_ffmpeg/src/streamffmpeg.cpp) camera 相关函数

**现状**（从近期 commit 信息推断）：
- 摄像头模式切换到别的模式再切回来时，分辨率列表丢失
- 设备枚举和分辨率获取可能是每次切换时重新执行
- dshow 设备枚举是阻塞且耗时操作（Windows 上 1-5 秒）

**阻塞点**：
- dshow 设备枚举 API 调用耗时
- 相机初始化/启动耗时

**优化方案**：
- 首次枚举后缓存设备列表和分辨率列表
- 在后台线程预热摄像头（预先 `avformat_open_input`）
- 模式切换时直接复用已缓存的设备信息

**预估提升**：模式切换加速 1-2 秒

### P11 — FFmpeg 全局日志回调优化

**文件**：[streamffmpeg.cpp](backend/stream_ffmpeg/src/streamffmpeg.cpp) `StreamFFmpeg` 构造函数中的 `av_log_set_callback`

**现状**：
```cpp
av_log_set_callback([](void*, int level, const char* fmt, va_list vl) {
    if (level > av_log_get_level()) return;
    static char buf[2048];
    static std::mutex mtx;
    {
        std::lock_guard<std::mutex> lock(mtx);
        vsnprintf(buf, sizeof(buf), fmt, vl);
    }
    // ... 字符串处理 + LOG_XXX
});
```

**阻塞点**：
- **全局互斥锁** — 所有 FFmpeg 内部线程共享同一把锁
- `vsnprintf` 2048 字符在锁内
- 当前级别设置为 `AV_LOG_ERROR`，正常运行时影响不大，但问题排查时调高日志级别会显著影响性能

**优化方案**：
- 使用 `thread_local` buffer 消除全局锁
- 或者切换到 FFmpeg 内置的日志上下文机制（`av_log_set_context`）

**预估提升**：微小但持续，调试模式下效果明显

### P12 — 编码器预设参数调优

**文件**：[streamffmpeg.cpp](backend/stream_ffmpeg/src/streamffmpeg.cpp) 编码器配置部分（`pushScreenLoop` 等）

**现状**：
- 编码器使用默认 preset（通常是 medium/balanced）
- NVENC 编码器未设置 `-preset p1`（fastest）或 `-tune ll`（low latency）
- AMF 编码器类似，未配置低延迟参数

**阻塞点**：
- 默认 preset 偏重画质，编码延迟较高
- 推流场景下低延迟比画质更重要

**优化方案**：
- NVENC：添加 `-preset p1 -tune ll -zerolatency 1`
- AMF：添加 `-usage ultralowlatency`
- 软件编码（x264）：使用 `-preset ultrafast -tune zerolatency`
- 降低 `-rc-lookahead` 值

**预估提升**：编码延迟降低 30-50%，推流端到端延迟明显缩短

## 四、性能监控建议

当前系统缺乏量化的性能监控，建议在实施优化前先加入：

1. **帧耗时打点**：在 capture→encode→mux 关键节点记录时间戳，输出到调试日志
2. **OpenGL 帧率显示**：在 FGLWidget 中用 `QElapsedTimer` 统计 paintGL 调用间隔
3. **内存用量监控**：定期输出 `QByteArray` 大缓冲区的数量和总大小
4. **编码器统计**：利用 FFmpeg 的 `AVCodecContext::frame_number` 等字段输出编码帧率

这些数据可以在优化前后对比，量化优化效果。
