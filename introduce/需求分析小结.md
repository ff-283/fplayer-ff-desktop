# 需求分析小结

## 1. 需求层次与优先级

系统需求按优先级分为三级。P0 为最小可用边界，共十三个功能模块，包括本地播放、摄像头采集、屏幕捕获、文件推流、摄像头推流、屏幕推流、P2P 推流、拉流播放、媒体分发、会话管理 API、会话幂等、地址编排、启动编排和动态端口分配。这些功能缺失任何一项都会导致核心闭环断裂，是 MVP 必须实现的。

P1 为体验增强层，共十四个模块，包括多源合成推流、服务端推流、Electron UI、Kernel Console、日志管理、跨平台发布、图池管理、系统设置、三端协同链路等，在核心功能可用基础上显著提升系统完整性和用户体验。

P2 为差异化功能，当前仅 AI 视觉分析一项。

## 2. 关键取舍

需求分析过程中的若干取舍有明确的技术和业务理由。不做鉴权是因为目标用户以内网可信环境为主，且架构已预留中间件扩展点；不做持久化数据库是因为流会话生命周期短，内存存储即可满足，引入数据库反而增加部署复杂度；不做转码编排是因为硬件编码已覆盖主要需求，转码会增加系统复杂度和资源消耗；移动端仅做播放不做采集推流，集中资源保障播放体验；不做 iOS 支持是因为开发设备和测试条件受限，优先保障 Android 和 Web 平台。

## 3. 实现状态与迭代规划

当前状态：P0 和 P1 全部模块已实现，P2（AI 分析）也已实现，核心功能实现率达到百分之百。后续规划分两个阶段。生产就绪阶段引入鉴权体系、Redis 持久化、Prometheus 监控和自动化测试。企业级扩展阶段探索集群化部署、WebRTC 超低延迟、自适应码率转码和服务端录制回放。

## 4. 总结

FPlayer 的需求分析围绕局域网流媒体一体化展开，一百四十二条功能需求和九十五条非功能需求覆盖了从采集、分发到播放的完整链路。系统在鉴权、持久化、集群等方面的取舍服务于"开箱即用、零依赖部署"的设计目标，架构为后续演进预留了充分的扩展空间。
