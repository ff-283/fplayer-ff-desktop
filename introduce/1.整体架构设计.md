# 整体架构设计

## 1. 系统概述

FPlayer 是一个三端协同的局域网流媒体采集、分发与播放系统。系统由**桌面客户端**（采集与推流）、**流媒体服务端**（分发与编排）和**移动/网页播放端**（拉流播放）三部分组成，覆盖从音视频采集、编码推流、服务端分发到终端播放的完整链路。

系统的核心设计理念是**控制面与数据面分离**：服务端负责会话管理与地址编排（控制面），媒体分发内核负责实际的流媒体传输（数据面），桌面客户端和移动端仅作为流的生产者和消费者。

## 3. 三端职责划分

### 3.1 桌面客户端（fplayer-ff-desktop）

桌面客户端是整个系统的**流生产者**，负责音视频的采集、编码和推流。基于 C++17 和 Qt6 构建，集成 FFmpeg 作为媒体处理核心。

核心能力：
- **多源采集**：支持本地视频文件播放、摄像头采集、屏幕捕获（含 DXGI 硬件加速）
- **多源合成**：支持将多个采集源组合到一个画布中进行合成推流（Compose Mode）
- **编码推流**：利用 FFmpeg 进行 H.264/H.265 硬件编码，推流到服务端或直连对端
- **拉流播放**：支持从服务端或对端拉流播放和录制
- **AI 视觉分析**：集成 OpenAI 兼容接口，支持对截图进行 AI 分析

### 3.2 流媒体服务端（fplayer-ff-service）

服务端是系统的**控制中枢与分发核心**，负责会话管理、地址编排和媒体流分发。采用"媒体内核 + 网关 + 管理界面"的组合架构。

核心能力：
- **媒体分发**：内置 ZLMediaKit 内核，支持 RTMP/RTSP/HLS/HTTP-FLV 多协议分发
- **会话编排**：Go 语言编写的 Gateway 提供 RESTful API，管理流的创建、查询、停止
- **地址解析**：客户端通过 app/stream 名称即可获取可播放地址，屏蔽端口动态变化
- **管理界面**：Electron 桌面 UI，提供可视化的流管理、日志查看和配置操作
- **控制台模式**：独立 Go 编写的 kernel-console，支持命令行部署和前台驻留

### 3.3 移动/网页播放端（fplayer-ff-mobile + FPlayer-WebSite）

移动端和网页端是系统的**流消费者**，专注于流媒体播放体验。

核心能力：
- **移动端**（Flutter）：基于 media_kit（libmpv 封装）实现 HLS/HTTP-FLV/RTMP 多协议播放
- **服务地址模式**：通过网关 API 自动解析播放地址，无需手动拼接 URL
- **直连模式**：支持直接输入流地址进行播放
- **网页端**：产品展示页面，展示系统功能和应用场景

## 4. 分层架构

系统整体采用四层架构设计：

```
┌─────────────────────────────────────────────┐
│              表现层 (Presentation)            │
│  桌面: Qt6 Widgets (CaptureWindow)           │
│  服务: Electron UI + kernel-console          │
│  移动: Flutter Material 3                    │
├─────────────────────────────────────────────┤
│              服务层 (Service)                 │

│              运行时层 (Runtime)               │

│  移动: media_kit (libmpv + FFmpeg)          │
└─────────────────────────────────────────────┘
```

## 5. 两种工作模式

### 5.1 P2P 直连模式

适用于一对一、局域网临时连线的场景。推流端直接将流推送到目标地址，拉流端直接从该地址拉流，不经过服务端。

- 优点：链路最短、延迟最低、无需额外部署
- 缺点：无法一对多分发、无协议转换、无会话管理

### 5.2 服务分发模式

适用于一对多、多对多、跨端兼容的场景。推流端先向服务端创建会话，获取服务端返回的推流地址后再推流；拉流端通过服务端 API 解析播放地址后拉流。

- 优点：统一分发、协议自动转换（RTMP→HTTP-FLV/HLS）、会话集中管理、地址动态编排
- 缺点：增加一跳网络延迟、需额外部署服务端

## 7. 通信协议体系

系统内部和系统之间采用多种通信协议：

- **控制面协议**：HTTP RESTful API（JSON），用于会话管理、地址解析、健康检查
- **数据面协议**：RTMP（推流）、HTTP-FLV（低延迟拉流）、HLS（兼容性拉流）、RTSP（可选）
- **进程间通信**：Electron IPC（contextBridge）、环境变量传递（端口配置）
- **运行时信息交换**：runtime.json 文件（端口与端点快照）

各协议的具体设计详见《流媒体传输协议设计》章节。

## 8. 部署架构

系统支持三种部署形态：

1. **纯局域网部署**：服务端部署在局域网内任意主机，桌面端和移动端通过局域网 IP 访问
2. **公网部署**：服务端部署在公网服务器，通过 `SERVICE_PUBLIC_HOST` 配置公网地址，支持 FRP 反向代理
3. **便携版部署**：Windows 下提供 portable-ui 和 portable-kernel 两种免安装包，解压即用

## 9. 关键设计决策

### 9.1 控制面与数据面分离

Gateway 仅管理会话元数据和地址编排，不介入媒体数据的实际传输。ZLMediaKit 独立完成所有媒体协议的处理和分发。这种设计使得控制面和数据面可以独立扩缩容、独立故障恢复。

### 9.2 无数据库设计

当前版本中，Gateway 使用内存 map 存储会话信息，不依赖外部数据库。runtime.json 文件作为运行时的端口快照供外部消费者读取。这种设计简化了部署依赖，适合单节点场景。会话数据在 Gateway 重启后丢失，未来可扩展 Redis/MySQL 持久化。

### 9.3 策略模式与后端可替换

桌面客户端采用策略模式，通过 Runtime 工厂层根据配置选择具体的后端实现（FFmpeg/Qt6/DXGI）。所有后端实现统一的 API 接口（IPlayer、ICamera、IScreenCapture、IStream），使得后端可以按需替换而无需修改上层代码。

### 9.4 动态端口分配

所有服务端口在启动时动态探测空闲端口，避免端口冲突。ZLMediaKit 配置文件在运行时由模板动态生成。Gateway 支持自动换端口重试（最多 8 次）。这使得多个服务实例可以在同一主机上并行运行。

### 9.5 跨平台抽象

桌面客户端将平台特定代码隔离在独立的源文件中（如 WASAPI 音频采集仅 Windows 编译，DXGI 仅 Windows 启用）。NativeWindow 结构体通过平台条件编译携带不同的窗口句柄类型。服务端通过构建标签和运行时判断实现 Windows/Linux 兼容。
